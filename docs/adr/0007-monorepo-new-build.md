# New monorepo for the backend and frontend; `mikrotik-login` is prior art only

The Backend and the purchase web app are built fresh in this repository as a monorepo (`backend/` + `frontend/`), alongside the existing Login Page and its ADRs, instead of replacing or extending the sibling `~/Projects/mikrotik-login` monorepo that already ships a Go backend and a Svelte admin app.

The two designs share a business problem but not a domain model: this repo sells **Package** + **Active Period** with **Phone Number + PIN** / **Access Code** / **User** credentials provisioned by writing to **FreeRADIUS** (ADR 0001), app login via **Magic Link** (ADR 0003), and **Extend** on a live Active Period. `mikrotik-login` sells pre-generated **Voucher** stock through Tripay over the **MikroTik API** with a command queue, dual-token auth, and multi-router sync — its own ADRs 0004, 0005, 0007, 0008, 0010 all encode decisions this repo's glossary explicitly rejects (it lists **Voucher** as a term to avoid). Extending that monorepo would mean superseding five or more of its ADRs and migrating live voucher data.

Consequences: this repo owns one `CONTEXT.md`, one ADR sequence (continuing at 0007), one docker-compose, and the API contract between its own `backend/` and `frontend/`; code and patterns may be read from `mikrotik-login` (payment gateway integration, worker queue, auth) but never copied with its vocabulary. Rejected alternatives: converting the existing monorepo in place (ADR churn plus data migration for a different product model) and splitting backend and frontend into separate repositories (manual contract drift, heavier coordination).
