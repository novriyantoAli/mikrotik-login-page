# Payments via Tripay, behind a PaymentGateway port

The backend creates and settles payments through **Tripay**, hidden behind a `PaymentGateway` interface in the payment domain so that the Transaction service never imports a vendor SDK, HTTP client, or Tripay-specific status code. Tripay was chosen because the sibling `mikrotik-login` monorepo already runs it in production — sandbox credentials, webhook signature handling, and closed-payment (VA/QRIS) channel codes are known quantities rather than assumptions — and because its closed-payment channels fit a captive-portal checkout where the buyer must stay inside the app. The port keeps the vendor boundary testable (a fake gateway drives the Transaction tests) and leaves room for a second provider per deployment or for a fallback if Tripay is unavailable.

Consequences: the payment domain owns the port plus a Tripay adapter that maps Tripay's status vocabulary onto this repo's Transaction states; the adapter alone knows merchant codes, signatures, and channel identifiers, and no Tripay type crosses into the Transaction service or the HTTP DTOs. Checkout uses Tripay's closed-payment channels rendered inside the app (VA/QRIS plus instructions) rather than a hosted redirect, so the backend also exposes a read-only status endpoint per Transaction that the app polls until the payment settles; the gateway callback stays the authoritative settlement signal. Rejected alternatives: Midtrans (better documentation and SDK, but higher fees and no existing code to learn from) and manual bank transfer with admin confirmation (no automated settlement, so every purchase needs a human, and the "successful purchase" trigger described in ADR 0004 would have no reliable signal).
