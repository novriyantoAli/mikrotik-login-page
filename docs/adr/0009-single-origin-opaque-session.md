# Single-origin deployment with an opaque session cookie

The purchase app is served by the reverse proxy of the same host that proxies `/api` to the Go backend, so browser and API share one origin. After a Magic Link is exchanged, the backend issues a random session token, stores only its hash in Postgres, and sets it as an `HttpOnly`, `SameSite=Lax` cookie valid for 30 days and revocable per session; there is no JWT, no access/refresh pair, and no CORS configuration.

Chosen because the system is self-hosted on the machine that also holds the Wavecom modem (ADR 0003), so a single origin costs nothing extra and removes a whole class of failure — no preflight, no cookie-domain mismatch, no third-party token storage. An opaque server-side session is privileged over a JWT here because the only identity is a Phone Number with no password to change (ADR 0004/0008): if a session leaks, revocation must be immediate, and a bearer token readable by JavaScript would be the easiest thing to steal. The 30-day lifetime matches how rarely a buyer returns rather than how long a login should idle.

Consequences: the frontend must never call the API cross-origin, so local development runs the same proxy (or Vite's proxy), and any future mobile client would need its own auth path. Rejected alternatives: separate `app.` and `api.` subdomains with CORS and bearer tokens (more moving parts for no benefit at this scale, and the pattern borrowed from `mikrotik-login` exists there because that app targets a different deployment) and a single long-lived JWT in a cookie (fewer components, but a stolen token stays valid until expiry with no way to revoke it).
